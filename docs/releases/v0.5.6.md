# Tote 0.5.6

DSH connection controls now follow the page's actual response. A successful login shows the app without a lingering sign-in banner or the misleading “not saved in settings” message.

## What changed

- Submitting a startup link shows “Connecting…” until the local page responds. A successful response hides the connection form and transfers focus from the form into the app.
- A queued Retry does not reload an already connected page or discard its unsent draft.
- New panes reuse the provider's existing login cookie. An expired login restores the form; HTTP errors and failed loads display a connection problem instead of claiming success.
- Invalid-link guidance explicitly accepts both `http://` and `https://` localhost URLs. Startup tokens still stay out of provider settings and layouts.

## Upgrade

Use **Settings → About → Check for updates → Download → Install** on Linux AppImage. This viewer fix does not require restarting the background host or its agent sessions. Android advances to versionCode 18 with no Android behavior changes, the same production signing identity and lineage, and wire protocol v1.

## Verification and limits

The provider UI regression checks authentication rejection, successful login, hidden connection controls, draft preservation on Retry, cookie reuse in a fresh pane, expired/invalid login and server errors. The real running DSH server was also opened in an isolated Tote profile: it returned HTTP 200, rendered its app, hid the connection controls and remained authenticated after Retry. Unit tests and the release pipeline cover the remaining desktop/mobile and packaged-runtime checks.

Physical phone testing remains deferred; this desktop UI fix makes no new claims about phone-specific behavior.
